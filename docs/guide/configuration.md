# Configuration

[Back to the README](../../README.md)

## Settings and where files are

`/settings` shows every setting under headings (Model, Display, Input, Conversation, Tools and safety, Commands and sets), each with a line saying what it does; typing shows only the settings whose name, value, heading or description has each word typed; also each command's next steps, publication approval, and what the session loaded from where, with any problems (Enter on a file opens it in `$EDITOR`).

Scramjet's settings (`~/.config/scramjet/settings.json`) and sessions (`~/.local/state/scramjet/sessions/`, or `--session-dir`) are apart from Scramjet 1's, with the same setting names. Your own agents (`~/.config/scramjet/agents`), skills (`~/.config/scramjet/skills`), themes, `SYSTEM.md` and global `CLAUDE.md`/`AGENTS.md` are in `~/.config/scramjet/` too. It shares Scramjet 1's `autonomy.yaml` files (the next steps that continue by themselves), `~/.config/scramjet/autonomy.yaml` included. [Where Scramjet keeps its files](install.md#where-scramjet-keeps-its-files) lists the rest.

## Context files and skills

Both `CLAUDE.md` and `AGENTS.md` are read, from `~/.config/scramjet`, the project and the directories above it, and after them each directory's `CLAUDE.local.md`: your own notes, kept out of version control, as in Claude Code. Skills are directories with a `SKILL.md`, found in `.scramjet/skills`, `.agents/skills`, the command sets, `~/.config/scramjet/skills` and `~/.agents/skills`; `/skill:<name>` runs one.

## Credentials

The agent's tools see what you see, `gh`'s login and the ssh-agent included, in every turn. With the `hideCredentials` setting `unattended` (turns nobody started: a next step that runs by itself, autopilot, `-p`) or `always`, they cannot see common credential stores (`~/.ssh`, `~/.netrc`, …), those `models.json` files name, or credential variables; `--list-credential-stores` lists the stores. On WSL a Windows program a command runs (`cmd.exe`, `powershell.exe`) still reads them through `\\wsl.localhost\`, so that Windows programs keep working in those turns. No instruction file (`CLAUDE.md`, `AGENTS.md`, `SYSTEM.md`) is read from one, also through a link, and a command that failed for want of one is told why, so that the agent asks you or goes on without it. tmux servers the agent starts then get their own socket directory: attach with `TMUX_TMPDIR=~/.local/state/scramjet/tmux tmux attach`. Commands never get the terminal, so a passphrase or password prompt fails at once rather than wait.

## The sandbox

Tool calls run without asking; there is no permission mode, and by default the main agent's shell is not sandboxed (beyond hiding credential stores when `hideCredentials` asks, [above](#credentials)). `--sandbox read-only` or `workspace-write` (`-s`, or the `sandbox` setting), as Codex names them, runs it under Bubblewrap as subagents' is, with the project writable in `workspace-write` but its own `.git`, `.scramjet` and `.agents` (repositories nested in it stay writable, as in Codex), and refuses the writes and edits it does not allow; commands reach the network unless `sandbox.network` is `false`, which keeps them off it with no sandbox too, said at every start: on Linux they then run under Bubblewrap with the files as they are but the network unshared (the internet, the local network and this machine's own servers) and `/run`'s sockets hidden (D-Bus, Docker's, WSL's way to Windows' programs), Unix sockets elsewhere, as in `/tmp`, left open; on macOS Seatbelt closes every socket (untried); on Windows nothing can, so the Network row says it stays on. A `!` command, which you run, keeps the network. The `sandbox` setting is an object of Claude Code's shape with Codex's modes, `{"mode": "workspace-write", "network": false, "filesystem": {"allowWrite": ["~/scratch"], "denyRead": ["~/notes"], "allowRead": ["~/notes/shared"]}}` (a mode's name alone and `sandboxNetwork` are still read): `allowWrite` (Codex's `writable_roots` is read too) makes directories writable in the sandbox in every project, such as a tool's cache in the home directory (uv's `~/.cache/uv`, which `uv run` writes), and `denyRead` hides files and directories as the credential stores are hidden, from commands, `read`, `grep` and `find` and from subagents, in the turns that hide the stores (`hideCredentials`, and every turn in the sandbox); `allowRead` makes what is in a `denyRead` directory readable again (writable where it would be), but never a credential store, which only `hideCredentials` shows, and what `denyRead` names deeper in it stays hidden; the project and the directories the sandbox makes writable are re-opened so too; `~` and relative paths are taken from the settings file's directory. Subagents stay read-only and off the network whatever the main agent's sandbox; `sandbox.subagents` sets theirs apart: `{"network": true, "filesystem": {"denyRead": [...], "allowRead": [...]}}` lets their commands reach the network, and each list given replaces the main agent's for them (without one they take the main agent's). `{"mode": "workspace-write"}` lets a subagent whose agent file lists `write` or `edit` write in its working directory (the project, or the task's `cwd`), its `.git`, `.scramjet` and `.agents` kept read-only, and its commands then run in a sandbox where only that directory is writable; `"filesystem": {"allowWrite": [...]}` adds directories writable to such subagents (with `"mode": "read-only"`, only those). An agent file that lists no tools keeps the read-only ones. With the main agent's own sandbox on, a subagent writes only where the main agent may as well, so `--sandbox read-only` keeps every subagent read-only too. Subagents running at once share the directory: give parallel writers separate `cwd`s, or worktrees: `isolation: worktree` in an agent's file, or `"isolation": "worktree"` in a task, as in Claude Code, runs each of its tasks in a git worktree of its own (a chain's steps that ask for one share it, so each sees what the earlier changed), on a new branch `worktree-agent-…` from the repository's `HEAD` (uncommitted changes are not in it), made under the state directory's `worktrees/` (`~/.local/state/scramjet/worktrees/<project>/agent-…`), writable to it even when the main agent's sandbox is not, its git files read-only, so it leaves its changes uncommitted; a worktree it left unchanged is removed with its branch (files git ignores in it, such as build output, an ignored notes directory or a `.env`, go with it, as in Claude Code, and the result names them), else the result names its path and branch, and you or the main agent remove it once its changes are taken or dropped. On Windows subagents cannot write. `"blockReadsOutsideWorkingDirectories": true` (Claude Code's key, read under `permissions` too) keeps the agent to the project: the home directory, the other users' homes and mounted drives (`/mnt`, WSL's Windows drives among them, and `/media`) are hidden but for the project, the directories the sandbox makes writable, the command sets', skills' and agents' directories, this project's sessions and, where the project is a linked worktree, its repository's Git directories, each directory on `PATH` in the home directory with its install prefix and where its programs' symlinks lead (`~/.cargo`, `~/.nvm/versions/node/…`, `~/.local/share/claude/versions`), `~/.rustup` and uv's `~/.local/share/uv`, and git's `~/.gitconfig` and `~/.config/git`; `allowRead` re-opens more, and system directories stay readable. `"blockReadsOutsideWorkingDirectories": "minimal"` (after Codex's `:minimal`) hides more: everything at the top of `/` but the system's own directories (`/usr`, `/etc`, `/opt`, `/bin`, `/sbin`, the `/lib` directories, and `/dev`, `/proc`, `/sys`, `/tmp` and `/run`), so `/var`, `/srv` and a site's `/scratch` or `/nix` too, and in the home directory only the project, the writable directories and what Scramjet gives the agent, not `PATH`'s programs, the toolchains or git's configuration: `allowRead` re-opens what a task needs. On macOS it keeps `/System`, `/Library`, `/Applications` and `/private` too (untried), and on Windows it is the project-only reach. On Windows the home directory and the other users' profiles (`C:\Users`) are hidden, the temporary directory kept, and since nothing there can hide files from commands, the first command says that only `read`, `grep` and `find` keep to the reach. `read`, `grep` and `find` keep to it always, and commands too, without a sandbox as well on Linux and macOS (everything else stays writable to them, what the reach hides stays hidden and unchanged but `allowWrite`'s directories and those `--add-dir`, `/add-dir` and the screen's Also writable add, which stay readable and writable, their tmux servers get their own socket directory as with `hideCredentials`, and the credential variables and stores outside the reach stay as `hideCredentials` says; untried on macOS), and subagents' always, with the main agent's writable directories (`/add-dir`'s too) kept in their reach (`sandbox.subagents.blockReadsOutsideWorkingDirectories` sets theirs apart). `/sandbox` (or Codex's `/permissions`, and `/settings`' Sandbox row) opens one screen for all of it, in plain rows: **Can change** (nothing, this project, or anything with no sandbox: the modes), **Can read** (everything you can, this project and your tools, or this project and the system only: the reaches; on Windows "read, grep and find only", as nothing there keeps commands to it), **Network**, the lists **Also writable** (the directories granted, `allowWrite`'s marked "every project" and this project's "set here"; with no sandbox, shown while Can read hides something, as what it then re-opens), **Hidden** (`denyRead`) and **Also readable** (`allowRead`), each with Add… and Enter on a path to take it out, and **Subagents**, opening the same rows for `sandbox.subagents` ("same as the main agent" where they take its reach or lists). A change applies at once, the reach too, and is remembered for this project: the next session here, a resumed one too, starts with it, and `/reload` keeps it. A project keeps only the rows changed in it, marked "(set here)", and a default's path taken out there shows as "(taken out here)" to put back; the other rows follow the default, so a default changed later reaches them. Ctrl+R resets the project to the defaults, once confirmed, forgetting its rows and the directories granted always here; Ctrl+S saves the sandbox as it is then as every project's default in your settings, and the project then follows it (the directories granted only for the session, or always here through `request_permissions`, stay out of `allowWrite`). What each project changed is kept by the project's path in `sandbox-projects.json` beside your settings, never in the repository, so a cloned repository cannot loosen its own sandbox; `--sandbox` at start still wins over it for that session. `/sandbox MODE`, `network on|off` and `remove DIR` change it at once without the screen, remembered as the screen's changes are, and `add DIR` for the session only; `/add-dir DIR` (or `--add-dir DIR` at start, as in Claude Code) makes another directory writable too, its own `.git`, `.scramjet` and `.agents` kept read-only unless granted by name; with no sandbox it only re-opens a directory Can read hides. The agent is told what is writable, and asks for more with `request_permissions`, naming the directories and why; you allow it for the session, always for this project (kept by the project's path in `sandbox-grants.json` beside your settings, never in the repository, listed by `/sandbox` and forgotten by `/sandbox remove DIR`), or deny it (in `-p` and steps autopilot runs, no one answers, so it is refused). On Linux, `sandbox.launcher` names a program started with Bubblewrap's arguments in `bwrap`'s place, such as a wrapper for machines where `bwrap` alone cannot start (a name alone is found on `PATH`, a path is taken as `allowWrite`'s are); it serves the stores hidden by `hideCredentials` and subagents' commands too, and macOS and Windows ignore it. MCP servers run outside it, with your environment and credential stores, as in Codex and Claude Code: they are programs you configured, not the agent's, and changing the sandbox does not restart them. `--ask` asks before every shell command and every write or edit outside the project, as a way to watch, not containment. Use Git, a clone or a worktree to recover.

Two agents are there without any command set: `scramjet:explore`, which finds where something is in the code, traces how it flows or maps what depends on what, and answers with cited evidence and what it could not establish (the breadth asked: quick, medium or very thorough); and `scramjet:general-purpose`, for multi-step investigations that need judgment. The agent's instructions list these, your own agents (`~/.config/scramjet/agents`) and the command sets', as Claude Code lists its agents; a project's `.scramjet/agents` are reached with the call's `agentScope` and your approval, and are not listed. Subagents run inside this process, read-only unless `sandbox.subagents` lets them write ([above](#the-sandbox)): their shell runs under Bubblewrap with every file read-only, a private `/tmp`, no network and credential stores hidden (on macOS, Seatbelt, with `/tmp` and `TMPDIR` writable and shared, as in Codex; on Windows, the low integrity level, with a `TEMP` of its own, the network, and nothing hidden).

## MCP servers

MCP servers come from the settings' `mcpServers`, as Claude Code's `.mcp.json` lists them: programs (`{"time": {"command": "uvx", "args": ["mcp-server-time"]}}`) and servers over streamable HTTP (`{"docs": {"type": "http", "url": "https://…", "headers": {"Authorization": "Bearer ${DOCS_TOKEN}"}}}`), with `${VAR}` and `${VAR:-default}` taken from the environment; no OAuth sign-in yet. The model finds their tools with `mcp_search` and runs one with `mcp_call`; the tools of servers that fit in 2% of the model's context window are also in its tool list, as `mcp__SERVER__TOOL` (Claude Code's names). Which are is decided once every server has started, so the tool list stays the same while they run; `/mcp` shows how each server is and how its tools are offered, a server that failed or ended starts again when the model uses it a minute or more later, `/mcp reconnect [SERVER]` starts one again at once, or all, and `/mcp enable|disable [SERVER]` starts or stops one, or all, as Claude Code's, saved in the settings' `disabledMcpServers`. No hooks or plugins.

## Themes, looks, banners and bottoms

The themes are `scramjet-dark`, its light companion `scramjet-light` and Pi's `pi-light`, each painting its own background and text color, so they look alike in every terminal, the default following the terminal's background (`scramjet-light` on a light one, as the terminal answers or `COLORFGBG` says), `terminal-colors` (the terminal's own 16 colors), and theme files in Scramjet 1's format from `~/.config/scramjet/themes/`, the project's `.scramjet/themes/`, the files and directories of the `themes` setting and `--theme`, chosen in `/settings` (`theme`). The theme in use shows each save of its file at once; `/reload` reads them all again. Beyond Scramjet 1's format, a theme's `colors` may hold a main `background`, which the full screen paints under everything, with the theme's `text` color over it. `/settings` → Theme → New theme… makes one: choose 1–5 main colors and a harmony, a dark or light background of its own or the terminal's (asked of the terminal, else as `COLORFGBG` says), roll (R) until it is close, lock (L) the colors you like and roll again, step toward the harmony (H) or the contrast (+/−), make the background lighter or darker (Lightness), move a main color up or down (Alt+Up, Alt+Down; the first tints the background), undo (U) and redo (Shift+U), while a sample session shows it. Tab lists every role (all 52 colors, each with its contrast and what it colors), where Left and Right make one follow another main color and `#` sets it to an exact color. Enter names the theme and saves it in `~/.config/scramjet/themes/`; once it is in use, Edit NAME… in the same list opens it again, and saving it under its name replaces it. Another theme in use with exact colors (`scramjet-dark`, `scramjet-light`, `pi-light`, a file of your own) offers New theme from NAME…, which starts from its colors: each role keeps that theme's color until a roll or a step changes what it follows. So does `terminal-colors` in a terminal that says what its 16 colors are (Windows Terminal does; tmux 3.0a does not), starting from the colors it shows.

The look is `tinted` by default: each prompt and call filled with the theme's background for a prompt and for how the call went, without sides, a rule above carrying the call and one below, inset a column, in the fill's state color (as `cards` in a theme without backgrounds). `/settings`' Look row also offers `panels` (each prompt and call on the theme's backgrounds, the default before 2.290.0), `classic` (a `●` before each call in the color of how it went, little else), `rails` (a rail beside each block, a call's in the color of how it went), `margin` (a column of labels down the left: who speaks, a call's tool in the color of how it went, the kind of notice), `cards` (a rounded card around each prompt, and around each call in the color of how it went, its tool, glyph and time on the top edge), `ribbons` (as `tinted`, its rules the fill's full width), `outline` (a log of actions, as Codex shows them: a `•` in the color of how each call went and a bold verb, its output under a `└`, and a rule saying how long a turn worked), `timeline` (one spine down the conversation, as `git log --graph` draws it, with a node on it for each prompt, reply and call, a call's `○`, `●` or `✗` in the color of how it went) and `mono` (no color but a failure's red: a call's `○`, `✓` or `✗` and the rail beside its output, dashed while it runs and heavy once it failed, say how it went, so it reads the same in any theme) (the `look` setting), each showing prompts, reasoning, tool calls and replies its own way.

The banner is `header` by default; `/settings`' Banner row also offers `plain` start lines, `card` and `logo`, Scramjet's logo (the `banner` setting). Ctrl+O expands them to every key and what was loaded.

The bottom of the screen (the status row, the prompt and the footer) is `bar` by default: `pi`'s prompt over a status bar, where the session is, then the output rate, the context's fill with a gauge, the cost and the model after a mark in the thinking level's color, with no background behind them. `/settings`' Bottom row also offers `pi`, the original bottom, with the session's token counts on its second footer row (the default before 2.290.0); `boxed`, the prompt in a rounded box in the thinking level's color and each dialog in a box of its own, with a footer that goes onto more rows rather than cutting anything on a narrow screen: where the session is and its modes, then the output rate, the context's fill and the cost, and the model; and `composer`, as Codex's, the prompt or a dialog on the prompt's background with an edge in the thinking level's color, the output rate, the context's fill, the cost and the model on the row under it, where the session is under them (the `bottom` setting). All but `pi` leave out the session's token counts and `auto`, which `/usage` and `/status` show. Every bottom shows the branch's open pull request after the branch, as `PR #N`, when the project's `origin` is on GitHub and `gh pr list` finds exactly one open from the branch; nothing when `gh` is missing or signed out. It is looked up again at the start, when the branch changes and after each turn or command.
